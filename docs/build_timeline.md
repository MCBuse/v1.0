# Build Timeline

**Operating model:** One developer + Claude Code. 4 hours/week baseline (Months 1 to 6), with capacity expected to increase from Month 7 once EXIST begins. Also this is opened up to the fact that more developers can join which will increase the MVP completion rate

View a visual timeline here: [https://claude.ai/public/artifacts/3372218f-2d01-42a9-8d9c-504dcd031f3f](https://claude.ai/public/artifacts/3372218f-2d01-42a9-8d9c-504dcd031f3f)

**Stack decisions (locked):**

- Extend the existing MCBuse pnpm/Turborepo monorepo
- Backend: existing NestJS API, new `data-capture` module cluster
- Frontend: the `apps/portal` Next.js PWA, with role-gated routes serving both the merchant dashboard and the admin panel. Expo app parked, not deleted.
- Payment-event source: Stripe sandbox. One static QR per merchant pointing to a Stripe Payment Link. Webhooks (`payment_intent.succeeded`, `charge.succeeded`, `payout.paid`, `payout.failed`, balance transactions) drive event capture and payout matching.
- NFC deferred to post-pilot. QR alone satisfies the capture requirement.

**Budget math:** 4 h/week gives roughly 17 h/month and about 110 h to the Month 7 MVP gate. The plan below assumes Claude Code handles scaffolding, migrations, test generation, and documentation drafts, and that your 4 hours are spent on decisions, review, and integration testing, not typing. Prefer one 4-hour deep session over four 1-hour fragments: context reload is your biggest tax at this cadence.

## Standing Rules for a 4-Hour Week

1. One deep session beats fragments. Book a single protected block.
2. Claude Code does first drafts of everything: code, migrations, tests, docs. Your hours are review, decisions, and E2E verification only.
3. Every session ends with a committed, working state and a one-line handoff note in the repo, so the next session starts cold-start-free.
4. Never build ahead of the frozen scope. The out-of-scope list in Section 3 of the team plan is your shield; use it in team meetings.
5. Weekly buffer discipline: W4-of-month is always partly buffer. A Stripe surprise costs a full week at this cadence, so the slack is structural, not optional.

## Top Risks Specific to This Plan

| Risk | Mitigation |
| --- | --- |
| Stripe sandbox payout timing does not mimic real payout cycles well enough to test matching | W4 spike verifies this early; fall back to simulated payout events injected via a test harness |
| EXIST hours do not materialize by Month 7 | Gate 2 escalation to Asim in W23; must-have list shrinks, deadline does not silently slip |
| Partner integration later diverges from Stripe event shapes | Ingestion is adapter-based from W15: raw provider event stored separately from structured event, so a partner adapter is additive |
| Review bottleneck: Claude Code produces faster than 4 h can review | Keep PRs small and single-purpose; reject any session output you cannot fully verify in-session |
